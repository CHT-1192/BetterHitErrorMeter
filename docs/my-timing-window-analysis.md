# ADOFAI 判定窗口 —— 我的逆向分析理解

> 基于对 Assembly-CSharp.dll 的完整反编译分析，结合官方文档验证

---

## 判定流程全貌

整个判定系统可以通过一个统一的视角来理解：**一切参数最终化为角度边界，然后取 Max(固定角度, 时间换算角度)**。

---

## 两种边界互相竞争

每个判定层（Counted / Perfect / Pure）都有一个**固定角度边界**（60° / 45° / 30°）和一个**时间换算角度边界**（基础时间 × 转速参数）。游戏取两者的较大值。

- **固定角度边界主导时**（低 BPM）：真实时间窗口大于标称值，对玩家额外宽容
- **时间换算角度主导时**（高 BPM）：固定时间窗口保持恒定，不再随 BPM 缩小

低 BPM 关卡实际判定比看起来宽得多——比如 BPM=60 时 60° 对应的时间窗口高达 333ms，相当于 0.333 秒的容错。BPM 越高这个窗口越窄，直到到达难度对应的最低时间窗口就不再缩小。

---

## 六个因素如何影响判定

### BPM

出现在两个地方：角速度的分子（BPM 越高行星转得越快），和角度→毫秒换算的分母（BPM 越高同样的角度代表的时间越短）。

**低 BPM（< ~220-500 取决于难度）**：固定 60° 主导，时间窗口 = 20000/BPM 毫秒，BPM 越高窗口越窄。
**高 BPM（> 上限）**：时间换算角度主导，时间窗口恒定 = 91ms / 65ms / 40ms，不再随 BPM 变化。

这也意味着制作低 BPM 的高难度谱面很难——因为判定天然就非常宽。

### 砖块速度倍率（Tile Speed）

和 BPM 的效果完全相同。tileSpeed × BPM 就是行星的实际转速。tileSpeed=2 等效于 BPM 翻倍的判定条件，但时间窗口不变（都被固定角度边界覆盖了）。

砖块速度基本不影响判定公平性，因为角度边界跟随转速同比例放缩，而时间窗口由基础时间决定。

### 砖块角度

砖块角度（entry 到 exit 的弧长）不直接影响判定窗口大小。但是影响两个次要方面：

- **Hold 判定**：弧长越长，hold 完成度的阈值越接近 1.0，需要按住行星走更远才能成功。短弧长 hold 更宽容。
- **飞过检测**：行星飞过 exit 超过半圈（π 弧度）视为失败。对大角度格子合理，对小角度格子其实不太可能触发。

### 音高（Pitch）

pitch 同时影响角速度和角度边界，**比例相同**——所以时间窗口本身不受 pitch 影响。pitch 的作用是改变角度→时间的换算倍率：

- pitch=2.0 时，同样的 10° 角度差只有 pitch=1.0 时的一半时间
- 这意味着音高谱面中，同一个角度误差代表更精确的时间精度

本质上 pitch 让判定在时间维度上保持不变，在角度维度上等比放缩。

### 飚速（Speed Trial）

唯一**直接缩小时间窗口**的因素。不是乘在 BPM 上——这是一个常见的误解——而是直接除以飚速倍率来缩小已计算的判定窗口。

基础时间 / 飚速倍率 = 实际时间窗口。1.5 倍飚速下 Normal 的 65ms 缩到 43ms，2 倍飚速缩到 32.5ms。

飚速受 25ms 硬下限保护。3 倍飚速下可能会出现原本层级化的判定（TooEarly / VeryEarly / Perfect）全部合并成 Perfect 的现象——因为 Perfect 的时间窗口（30ms）除以 3 = 10ms，被硬下限卡在 25ms；Counted 窗口（65ms）除以 3 ≈ 22ms，也被卡在 25ms。两者相同，所以中间层级消失。

### 难度选择

对应三个不同的基础时间阈值：

- 91ms（UI 显示为 "普通" / "宽判"）：BPM 超过 220 后固定
- 65ms（UI 显示为 "严格" / "中判"）：BPM 超过 308 后固定
- 40ms（UI 显示为 "严判"，仅自定义关卡）：BPM 超过 500 后固定

**命名澄清**：代码里的 `Difficulty.Lenient` 是玩家在游戏里看到的"宽判"（普通），`Difficulty.Normal` 是"严判"。代码命名和玩家看到的 UI 标签不一致。

三个难度在低 BPM（<220）下表现完全相同——都走固定 60° 边界，时间窗口由 BPM 决定。差异只在 BPM 很高时才体现。这就是为什么速度试炼在高 BPM 关卡（>340）下影响巨大，在低 BPM 下几乎无感。

---

## 两个保险机制

### 25ms 硬下限

所有判定类型（Counted / Perfect / Pure）的时间窗口都**绝对不会低于 25ms**。这是纯粹的人性化考虑——低于 25ms 的窗口人类几乎不可能稳定命中。

这个硬下限在速度试炼叠加严判时最容易触发。严格难度 2 倍速下 Perfect 的 30ms 变成 15ms，被硬下限拉回 25ms——等于 Conted（65ms 变 32.5ms）只比 Perfect 宽了 7.5ms。

### marginScale 的天然下限

关卡制作者可以用 "Timing Window Scale" 事件来缩小判定窗口（比如设 50% = 窗口减半）。但即使设到 10%，判定也有一个天然下限——因为缩放只影响固定角度边界，不影响时间换算角度边界。

结果就是制作者无法把判定缩得比 `baseTime × BPM × 3.0°` 更严。对于高 BPM 关卡这个下限依然有效；对于低 BPM 关卡，缩放几乎没有效果（因为固定 60° 本来就远超时间换算角度）。

---

## 移动版的独立逻辑

移动版和桌面版是两套判定系统：

- 基础时间窗口更大：90ms / 70ms / 50ms（桌面的 Counted 是 65ms / 40ms / 91ms 取决于难度）
- 不使用 BPM 上限机制——恒定 90ms 窗口
- 飚速直接乘在 BPM 上（而不是缩小窗口）——这意味着飚速在移动端的效果完全不同

---

## 关键误区澄清

**误区 1**："飚速是把 BPM 翻倍" → 错，飚速是直接缩小判定时间窗口，不改变 BPM 计算。

**误区 2**："高速关卡窗口更小" → 对但不全对。达到 BPM 上限后窗口就不再缩小了。700 BPM 关卡的实际判定窗口和 310 BPM 完全一样（如果选严判）。只是行星转得更快导致视觉上更难而已。

**误区 3**："严判对所有关卡都更严" → 错。BPM 低于 ~220 的关卡，三种难度的判定窗口完全相同。严判只在 BPM 高于 cap 时才体现差异。

**误区 4**："砖块角度影响判定" → 普通砖块的 entry/exit 角度不影响判定窗口。只影响 hold 格子的完成度阈值和飞过检测。

**误区 5**："Pitch 调整会改变判定难度" → pitch 同时改变角速度和角度边界，两者比例相同，时间窗口不变。但高 pitch 下同样的角度差换算出的时间误差更小——这对误差统计很重要。

---

## 判定系统的设计哲学

这个系统的设计逻辑是：在"人类能反应的范围内"保持判定公平。低 BPM 下如果严格按时间来，判定会过于宽松（因为 60° 等于很大的时间窗口）；高 BPM 下如果严格按角度来，判定会过于严苛。所以游戏取了时间的平衡点——低 BPM 用角度保底（阻止窗口宽到离谱），高 BPM 用时间保底（阻止窗口窄到不可能）。飚速和难度选择在这个框架上叠加额外的挑战性。
